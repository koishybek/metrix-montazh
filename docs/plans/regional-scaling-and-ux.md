4. Починить выбор модема (сделано, см. ниже).

### `node.additional_fields` — бэкенд сам диктует доп-поля (наследуется вниз по дереву)

- Алматы Су (18→20): `Код улицы в базе Алматы Су` + `Класс ИПУ` (B/C).
- Караганды Су (77): `Дата поверки` + `Код адреса` + `Район`.
- Все остальные (Туркестан, Кызылорда, Актау, тепловые сети, и сами узлы
  IoT-Exponenta 50/518/42/543/…): **`[]`** — никаких доп-полей.

Вывод: «код улицы есть только у Алматы» — частный случай. Правильно — **рендерить
доп-поля из `node.additional_fields` выбранного узла**, а не хардкодить Алматы Су.

### Поиск устройства (для UX) — уже используется в фиксе

Серверный `search` ищет по EUI + `description` (там лежит печатный серийник
`s/n: …`) + адресу. `serial_number` почти всегда `null`. Параметр `eui=` сломан
(возвращает всё) — использовать только `search`.

## Дизайн

### A. Выбор региона/водоканала (ОТКРЫТОЕ РЕШЕНИЕ — см. ниже)

После входа монтажник выбирает «Регион → Организация (сервисная компания)». Выбор
задаёт `meter.node`. Источник — дерево узлов с бэкенда, отфильтрованное до сервисных
компаний (type 17). Кэш в localStorage (TTL 24ч), как остальные справочники.

Развилка, которую должен решить владелец:
- **(A1) Полный список** всех сервисных компаний IoT-Exponenta — работает уже сейчас,
  но монтажник может выбрать чужой город по ошибке.
- **(A2) Только узлы аккаунта** — безопаснее, «реальный аккаунт решает». Но API не
  отдаёт «узлы пользователя» простым фильтром (`/user/` даёт только `groups`+`profile`;
  `node?users=` не фильтрует; наш токен — admin, скоупинг на нём не виден). Нужен
  тестовый аккаунт монтажника (НЕ admin), чтобы понять, фильтрует ли бэкенд дерево
  под обычного пользователя, либо доработка бэкенда (эндпоинт «мои узлы»).

Рекомендация: начать с A1 + запомнить выбор региона на устройстве; слой A2 навесить,
когда будет тестовый аккаунт/эндпоинт.

### B. Динамические доп-поля из `node.additional_fields`

Заменить хардкод Алматы Су (`almaty_su_street_id`, класс ИПУ, district) на рендер по
схеме `node.additional_fields`: `string` → текстовое поле, `select` → выбор из
`choices`. Значения собираются в `additional_data.*` по `name`. Для Алматы получится
ровно текущее поведение; для Караганды — её поля; для остальных — ничего.

### C. Регионализация геокодера

Город для геокодера и стартовые координаты карты брать из выбранного региона/узла, а
не хардкод «Алматы»/bbox Алматы/координаты Алматы. Если у узла нет геопривязки —
дефолт без bbox или поиск по всему КЗ.

### D. Payload

- `node` — из выбора региона (а не `cold→20/hot→256`).
- `resource_type` — оставить выбор ХВС/ГВС (и при необходимости расширить).
- `additional_data` — из динамической схемы (B), без жёсткого Алматы Су.

### E. Аккаунты и безопасность

- ✅ Вход — только реальные аккаунты SM, без захардкоженных тест-кредов (сделано).
- ⚠️ Из репозитория убрать `test_api.js`, `test_api.mjs`, `fetch-models.js`,
  `diagnose.js`, `debug-*.js` — в них закоммичен живой admin-токен и пароль.
  **Требует подтверждения на удаление + ротации токена/пароля на бэкенде.**
